# Logowanie: Microsoft + LinkedIn przy istniejącym e-mailu i Google + weryfikacja integracji LinkedIn

## Stan wyjściowy (zweryfikowany w kodzie — ważne odkrycie)

- **E-mail + hasło: działa** (rejestracja z polityką 12 znaków, HIBP, reset, anty-enumeracja — D04).
- **Google: już działa na prawdziwej integracji** — `AuthContext.tsx:255` robi `supabase.auth.signInWithOAuth({ provider: 'google' })`; incydent `google-user-1` to historia, przycisk jest prawdziwy od commita `caeab20`.
- **Brakuje: Microsoft i LinkedIn.** Sesja z OAuth wraca na `window.location.origin + '/'` i jest konsumowana przez `detectSessionInUrl: true` — ta ścieżka jest gotowa dla kolejnych dostawców, nic jej nie blokuje.
- Uwaga incydentowa (reguła 2): `AuthContext` ma martwy eksport `resendConfirmation` (bez konsumenta) — nie ruszamy w tej zmianie, ale nie kopiujemy tego wzorca.

## Weryfikacja integracji LinkedIn API (dostarczane w opisie PR + SETUP.md)

Fakty potwierdzone dzisiejszym sprawdzeniem dokumentacji LinkedIn i Supabase:
1. Stare „Sign In with LinkedIn" (`r_liteprofile`) jest **zastąpione** produktem **„Sign In with LinkedIn using OpenID Connect"** (scopes `openid`, `profile`, `email` — przyznawane automatycznie z produktem).
2. Supabase: jedyny obsługiwany identyfikator dostawcy to **`linkedin_oidc`** — legacy `linkedin` został **usunięty 04.01.2024**. Użycie starego id skończyłoby się błędem.
3. Callback dla aplikacji LinkedIn: `https://<ref>.supabase.co/auth/v1/callback` — musi być wpisany w LinkedIn → Auth → Authorized redirect URLs.
4. Aplikacja LinkedIn wymaga: strony LinkedIn (Page), logo, prośby o produkt OIDC i weryfikacji; po tym Client ID + Secret trafiają do Supabase → Authentication → Providers → LinkedIn (OIDC).
5. Microsoft (Azure): rejestracja aplikacji w Entra/Azure portal, redirect URI `https://<ref>.supabase.co/auth/v1/callback`, identyfikator dostawcy Supabase: `azure`.

## Zmiany w kodzie

**1. Rejestr dostawców — `src/lib/oauthProviders.ts` (nowy, czysty moduł):**
`OAuthProviderId = 'google' | 'azure' | 'linkedin_oidc'` + lista `{ id, label, queryParams }` (Google zachowuje `access_type=offline, prompt=select_account`; wspólny `prompt=select_account` dla pozostałych). Jedno źródło prawdy dla UI i kontekstu (reguła 3).

**2. `AuthContext.tsx`:**
- zamiast `signInWithGoogle` — generyczne `signInWithProvider(provider: OAuthProviderId)` korzystające z rejestru; `redirectTo: window.location.origin + '/'` bez zmian,
- migracja konsumentów: `AuthModal` (3 miejsca) i `StripeCheckoutModal` (bramka płatności, zostaje przy Google) — `signInWithGoogle` znika całkowicie (reguła 5),
- przy starcie sesji: wykrycie błędów OAuth w URL (np. `error=access_denied` po anulowaniu w dostawcy) → czysta funkcja mapująca na polski komunikat + wyczyszczenie parametrów istniejącym `stripAuthErrorParams` (działa na `error`/`error_description`, zachowuje `?checkout=success`). Komunikat ląduje jako baner w AuthModal — ekran nie ma prawo udawać, że nic się nie stało (reguła 2).

**3. `AuthModal.tsx`:**
- `GoogleButton` → generyczny `OAuthButton` (ikony: Google, Microsoft — cztery kwadraty, LinkedIn — „in"), wiersz trzech przycisków w widokach: wyboru, logowania i rejestracji (spójnie gate'owane `cloudAvailable`),
- osobny stan ładowania per dostawca (anulowanie Google nie blokuje kliknięcia Microsoft),
- baner błędu OAuth z punktu 2.

**4. Migracja SQL — lepszy `handle_new_user()`:**
Dzisiejszy trigger czyta tylko `display_name`, więc Microsoft/LinkedIn (które podają `name`/`full_name`) utworzyłyby profile z nazwą z prefiksu maila. `CREATE OR REPLACE FUNCTION` rozszerza łańcuch fallbacku: `display_name → full_name → name → preferred_username → prefix maila`. Bez zmiany samego triggera.

**5. Testy (Node, bez jsdom):**
- `src/lib/__tests__/oauthProviders.test.ts` — rejestr: poprawne id (w tym `linkedin_oidc`, nie `linkedin`), etykiety, queryParams,
- rozszerzenie `authErrors.test.ts` — mapa komunikatów OAuth (`access_denied` → anulowane; nieznane → generyczny, nigdy surowy tekst dostawcy; anty-enumeracja bez zmian),
- rozszerzenie `authRecovery.test.ts` — odczyt błędu OAuth z query/hash i zachowanie `?checkout=success` przy czyszczeniu.

**6. Dokumentacja:**
- `docs/SETUP.md`: sekcja „Microsoft i LinkedIn (OAuth)" — dokładne kroki z pkt „Weryfikacji" (portale, callback, produkt OIDC),
- `docs/polityka-prywatnosci.md` + `docs/rejestr-czynnosci.md`: nowe źródło danych (imię/nazwa, e-mail od dostawcy tożsamości przez Supabase; bez pobierania kontaktów ani danych z profilu beyond OIDC claims).

## Checklist operacyjny (po Twojej stronie, nie kod — trafi do SETUP.md)
